Bonus 11 — Planificateur et orchestration agentique

À quoi ça sert#

Le bonus 09-orchestration.md montre un orchestrateur qui enchaîne des agents. Ce bonus ajoute ce qui le rend fiable :

AjoutQuestion à laquelle il répond
Un planificateur séparéQui décide quoi faire, avant que quiconque agisse ?
Un plan approuvéÀ partir de quand un agent a-t-il le droit d'écrire ?
Un journal d'exécutionOù en est-on ? Que reprendre après une interruption ?
Des règles d'isolationComment faire travailler plusieurs agents en parallèle sans conflit ?
Un retour arrièreComment annuler proprement une étape ratée ?
Un cycle de vie des agentsComment ajouter, remplacer ou retirer un agent sans casser le reste ?

Principe directeur : planifier, faire approuver, agir, tracer. Aucune action avant l'approbation du plan.

1. Séparer planification, raisonnement et action#

PhaseQuiProduitDroits
Planifierplanificateur-backlogsprintdesk/resultats/plan-lot<N>.md (statut PROPOSÉ)Lecture + un seul fichier
ValiderHumainStatut APPROUVÉ, signé et daté—
Raisonner et agirReviewer, Rédacteur, Contrôleur (directement ou via l'orchestrateur)Livrables du planCeux de chaque agent
TracerOrchestrateur ou humainsprintdesk/resultats/journal-lot<N>.mdUn seul fichier

Pourquoi un fichier plutôt qu'un plan dans le chat ?

  • Il est inspectable : on le relit, on le compare, on le versionne.
  • Il est durable : il survit à la fermeture du chat et au résumé automatique du contexte.
  • Il est partageable : un autre agent ou un collègue peut reprendre le travail.

2. Pas à pas#

Étape 1 — Lancer le planificateur#

L'agent est fourni : .github/agents/planificateur-backlog.agent.md.

Nouveau chat, agent planificateur-backlog :

texte
Planifie le traitement du lot <N>. Ne lance aucune étape.

Attendu : le fichier sprintdesk/resultats/plan-lot<N>.md au statut PROPOSÉ, puis le bloc PLAN PRÊT. Aucun autre fichier n'est modifié.

Étape 2 — Relire le plan avec une grille#

ContrôleBon signeMauvais signe
Une étape = un agent, un livrable« 2. Réécrire — redacteur-backlog — sortie/lot<N>/ »« 2. Réécrire et contrôler »
Critère de fin vérifiable« verifier-us.cjs sans KO »« US de bonne qualité »
Autonomie classéeFusion et publication en « validation humaine »Aucune étape en validation humaine
ND-xx listées sans valeur« ND-02 : à trancher par le référent »« ND-02 : 5 Mo maximum »
Retour arrière décrit« revert du commit de l'étape 2 par PR »Rien, ou « supprimer les fichiers »

Étape 3 — Approuver ou faire réviser#

  • Réviser : RÉVISER : l'étape 3 doit citer le contrôle automatique. Le planificateur crée la version suivante, toujours PROPOSÉ.
  • Approuver : remplacer vous-même la ligne de statut par Statut : APPROUVÉ par <nom> le <date>.

Le planificateur n'a pas le droit d'écrire « APPROUVÉ ». C'est la porte entre le raisonnement et l'action.

Étape 4 — Exécuter le plan approuvé#

Deux options :

  • Manuel guidé : bouton de transfert (handoff) « Plan approuvé : lancer le diagnostic » en bas de la réponse du planificateur. Il ouvre reviewer-backlog avec un prompt prérempli, sans l'envoyer.
  • Orchestré : l'orchestrateur du bonus 09. Ajouter cette ligne à sa section « Déroulé », étape 0 :
    texte
    Lire sprintdesk/resultats/plan-lot<N>.md. Si la ligne Statut ne commence pas par « APPROUVÉ », s'arrêter et demander l'approbation.

Étape 5 — Tenir un journal d'exécution#

Créer sprintdesk/resultats/journal-lot<N>.md, mis à jour à la fin de chaque étape :

markdown
# Journal — lot <N> (plan version <n>)
| Horodatage | Étape | Agent | Résultat | Livrable | Commit | Décision humaine |
|---|---|---|---|---|---|---|
| 2026-05-12 10:02 | 1 Diagnostiquer | reviewer-backlog | fait | resultats/revue.md | 3f2a9c1 | VALIDER (C. Martin) |
| 2026-05-12 10:20 | 2 Réécrire | redacteur-backlog | partiel : US-<N>04 bloquée (ND-02) | sortie/lot<N>/ | 8b41d07 | CORRIGER |

Le journal sert à trois choses :

UsageExemple
Reprendre sans répéterAprès une interruption, on repart de la première étape non « fait ».
Détecter une dériveUn fichier modifié qui n'apparaît dans aucune étape = action hors plan, arrêt.
Revenir en arrièreLa colonne « Commit » donne le SHA à annuler (voir étape 7).

Committez après chaque étape validée : un commit par étape, c'est un point de retour par étape.

Étape 6 — Détecter et corriger une dérive#

Une dérive est un écart entre le plan et ce qui se passe réellement.

SignalCause probableRéaction
Un agent modifie un fichier hors de son livrableConsigne de délégation trop vagueArrêt, annulation du fichier, consigne précisée
Le rédacteur tranche une ND-xxInstruction ignoréeLe hook postToolUse et le check CI le signalent ; correction
L'orchestrateur saute un point de validationInterdit mal formuléCorriger l'agent, rejouer depuis le dernier point validé
Le contexte de session contient une ancienne version du planSession trop longue, résumé automatiqueNouvelle session, relire plan + journal (le hook sessionStart le rappelle à la reprise)

Étape 7 — Revenir en arrière proprement#

SituationActionÀ éviter
Étape locale ratée, pas encore committéegit restore sur les fichiers de l'étapeEffacer tout sortie/
Étape committée sur une branche de travailgit revert <sha> puis nouveau commitgit reset --hard sur une branche partagée
Étape déjà fusionnée dans mainWorkflow « Rollback backlog (revert par SHA) » : ouvre une PR de revertPush direct sur main
Publication déjà faiteWorkflow « Publication backlog » relancé avec le SHA d'une version saineSupprimer la release sans trace

Après un retour arrière : noter la ligne dans le journal, passer l'étape à « à faire », replanifier si nécessaire (nouvelle version du plan).

3. Orchestration agentique : les schémas#

SchémaPrincipeQuand l'utiliserRisque principal
Séquentiel (pipeline)A puis B puis CChaque étape dépend de la précédenteErreur en cascade
SuperviseurUn agent décide qui appelerDéroulé variable selon les résultatsSuperviseur qui fait le travail lui-même
Producteur-critiqueUn agent produit, un autre critique, on boucleQualité difficile à atteindre du premier coupBoucle sans fin : borner à 2 tours
Parallèle (fan-out / fan-in)Plusieurs agents sur des parties indépendantes, puis fusionGros volume, parties disjointesConflits à la fusion
Transfert (handoff)La conversation passe d'un agent à l'autreEnchaînement guidé par un humainContexte perdu si le transfert est mal rédigé

Travailler en parallèle sans se marcher dessus#

Exemple : traiter les lots 1 à 4 en même temps.

Règle d'isolationMise en œuvre SprintDesk
Un périmètre de fichiers par agentAgent A : sortie/lot1/ ; agent B : sortie/lot2/. Jamais deux agents sur le même lot.
Un espace de travail par agentUne branche par lot. Avec Copilot cloud agent : une issue par lot, chaque tâche a sa branche copilot/... et sa PR. En local : un worktree Git par agent.
Un fichier partagé = un seul écrivainsynthese-actions.md : chaque agent écrit synthese-lot<N>.md, la fusion est faite par une étape dédiée.
Fusion expliciteÉtape « fan-in » finale : contrôle global, puis une PR par lot ou une PR de consolidation.

Les trois conflits à reconnaître#

ConflitExemplePréventionRésolution
Modifications qui se chevauchentDeux agents réécrivent US-204Périmètres disjoints dans le planGarder une version, l'autre agent rejoue sur la base à jour
Travail en doubleDeux agents découpent la même USUne étape = un propriétaireSupprimer le doublon, noter dans le journal
Résultats contradictoiresLe reviewer dit « conforme », le contrôleur dit « KO »Critères communs (même script de contrôle)Escalade humaine : on ne laisse pas un agent trancher

Orchestrer avec Copilot cloud agent#

Pour un traitement en arrière-plan sur GitHub :

  1. Le planificateur prépare une prévisualisation des issues (un fichier, pas de publication).
  2. Un humain crée les issues et les assigne à Copilot.
  3. Chaque tâche travaille sur sa branche copilot/..., ouvre une PR brouillon et ne peut ni l'approuver ni la fusionner.
  4. Les workflows de la PR ne tournent qu'après « Approve and run workflows » par un humain (réglage par défaut).
  5. Les checks requis (« Format des US de sortie », « Politique - sources protégées ») et la revue humaine décident de la fusion.

4. Échecs et reprise#

Type d'exécutionSymptômeDiagnosticReprise
ÉchouéeErreur, aucun livrableJournal de session, dernière étape du journalCorriger la cause, relancer l'étape
Partielle3 US sur 5Comparer le plan, le journal et sortie/Relancer uniquement les US manquantes
BloquéeL'agent tourne en rond, ou attend une réponseBoucle producteur-critique, agentStop qui bloqueArrêter, escalader à l'humain, borner la boucle
Hors planFichier inattendu modifiéDifférence entre git status et les livrables du planAnnuler le fichier, préciser la consigne

Classer la cause avant de corriger (méthode du bonus 07-evaluation.md) : erreur de raisonnement (mauvaise conclusion), mauvais usage d'un outil (mauvais fichier, mauvaise commande), problème de contexte ou d'environnement (règle absente, fichier manquant, outil non installé).

5. Cycle de vie des agents#

OpérationBonne pratiquePourquoi
AjouterNouvel agent dans une PR, revue Code Owners, ajout à la liste agents: de l'orchestrateurLa liste fermée empêche un appel imprévu
ModifierPR + rejeu du jeu d'évaluation (bonus 07) avant fusionUn agent est identifié par la version du fichier au commit utilisé
RemplacerCréer redacteur-backlog-v2, comparer sur le même lot, puis basculer l'orchestrateurPas d'interruption : l'ancien reste disponible jusqu'à la bascule
RetirerRetirer de agents:, supprimer le fichier dans une PR qui explique pourquoiL'historique Git garde la version retirée : l'audit reste possible

Checklist#

  • ☐ Le plan existe en fichier, avec un statut et une version.
  • ☐ Aucune étape d'écriture n'a démarré avant APPROUVÉ.
  • ☐ Chaque étape a un critère de fin vérifiable et un retour arrière.
  • ☐ Le journal contient un commit par étape validée.
  • ☐ En parallèle : périmètres disjoints, un écrivain par fichier.
  • ☐ Les contradictions entre agents ont été tranchées par un humain.

Pièges#

  • Plan dans le chat seulement : il disparaît au résumé automatique et ne se relit pas.
  • Planificateur qui exécute : il « avance un peu » le diagnostic. C'est un défaut d'agent à corriger.
  • Approbation implicite : « ok » dans le chat n'est pas une approbation tracée.
  • Parallèle sur un fichier commun : deux agents écrivent synthese-actions.md.
  • Reset au lieu de revert : l'historique partagé est réécrit, l'audit est perdu.
  • Reprise depuis zéro : refaire une étape validée gaspille du temps et peut changer un résultat déjà accepté.

5 · Orchestration multi-agents

Orchestrate multi-agent coordination

15–20 % de l'examenFormation : chapitres 09, 11

Ce que dit le guide d'étude

CompétencePoints évalués
Opérer des workflows multi-agentsAppliquer un schéma d'orchestration ; isoler les agents en parallèle ; détecter et résoudre les conflits : modifications qui se chevauchent, travail en double, résultats contradictoires.
ObservabilitéArtefacts adaptés à la revue et à l'audit ; documenter décisions, transferts (handoffs) et résultats ; analyse a posteriori (post-hoc).
Échecs et dégradationRepérer les exécutions échouées, partielles ou bloquées ; réagir à une coordination dégradée ; schémas de reprise : rollback et humain dans la boucle.
Cycle de vieAjouter un agent ; le mettre à jour ou le remplacer sans perturber ; le retirer en gardant l'auditabilité et la continuité.

Schémas d'orchestration

SchémaPrincipeBon usageRisque
Séquentiel (pipeline)A → B → CDépendances fortes entre étapesErreur propagée
Superviseur / orchestrateurUn agent délègue à des sous-agents et consolideDéroulé variableSuperviseur qui fait le travail lui-même
Parallèle (fan-out / fan-in)Sous-tâches indépendantes, puis fusionGros volume, périmètres disjointsConflits à la fusion
Producteur-critique (generator / evaluator)L'un produit, l'autre évalue, on boucleQualité exigeanteBoucle infinie : borner
Transfert (handoff)La main passe d'un agent à l'autre avec un résuméEnchaînement guidé par l'humainContexte perdu si le transfert est pauvre

Mécanismes à connaître

  • Sous-agents (VS Code, CLI) : outil agent ; chaque sous-agent a un contexte isolé et ne renvoie que son résultat. Liste fermée d'agents appelables dans le profil de l'orchestrateur.
  • user-invocable: false : agent réservé à l'appel par un autre agent.
  • Handoffs (VS Code) : boutons de transfert avec prompt prérempli ; send: false pour laisser l'humain relire.
  • Cloud agent : une tâche = une branche = une PR ; plusieurs tâches en parallèle = plusieurs issues assignées.
  • Hook subagentStart : injecter les interdits dans chaque sous-agent (il ne peut pas bloquer). Hook subagentStop : bloquer une fin prématurée.

Isolation en parallèle

DimensionIsolation
FichiersPérimètres disjoints (un lot par agent)
Espace de travailUne branche ou un worktree Git par agent ; cloud agent : branche copilot/... par tâche
ContexteSous-agents à contexte isolé ; pas de conversation partagée
Fichier communUn seul écrivain ; les autres écrivent leur fichier, une étape fusionne
DroitsOutils et jetons propres à chaque rôle

Les trois conflits

ConflitDétectionRésolution
Modifications qui se chevauchentConflit Git, deux PR sur le même fichierRepartitionner ; l'un rejoue sur la base à jour ; fusion séquentielle
Travail en doubleDeux PR pour la même issuePropriétaire unique par tâche (assignation) ; fermer le doublon
Résultats contradictoiresReviewer « OK », contrôleur « KO »Critères communs et déterministes ; arbitrage humain

Observabilité

  • Chaque agent produit un artefact relisible : PR, revue, fichier de synthèse, journal.
  • Chaque transfert est documenté : qui passe la main, avec quel livrable, quelle décision humaine.
  • Analyse a posteriori : journaux de session, historique de la PR, check runs, audit log, journal d'exécution.

Échecs et reprise

ExécutionSignalRéponse
ÉchouéeErreur, pas de livrableClasser la cause, corriger, relancer l'étape
PartielleUne partie des livrablesRelancer seulement le manquant, depuis le dernier point validé
Bloquée (stalled)Pas de progrès, appels répétés, délai atteint (59 min pour le cloud agent)Arrêter, borner les boucles, escalader
DégradéeQualité en baisse, agents qui se contredisentRevenir au séquentiel, réduire l'autonomie, humain dans la boucle

Schémas de reprise : rollback (revert du commit de l'étape, redéploiement d'un SHA sain), point de reprise (journal), humain dans la boucle (validation avant de continuer).

Cycle de vie des agents

ActionComment, sans casser
AjouterPR + revue Code Owners + jeu d'évaluation ; ajouter à la liste des agents appelables
Mettre à jourPR ; la version d'un agent = SHA du fichier ; une PR en cours garde sa version
RemplacerNouvel agent à côté, comparaison sur les mêmes cas, puis bascule de l'orchestrateur
RetirerRetirer de la liste, supprimer par PR documentée ; l'historique Git garde l'audit

Pièges

Les erreurs classiques
  • Lancer plusieurs agents sur le même fichier « pour aller plus vite ».
  • Laisser un agent trancher entre deux résultats contradictoires.
  • Croire qu'un sous-agent voit tout l'historique de l'agent principal : son contexte est isolé.
  • Supprimer un agent sans PR ni trace : perte d'auditabilité.
  • Croire qu'une tâche cloud agent peut toucher plusieurs dépôts ou ouvrir plusieurs PR : non.

Trucs et astuces

Réflexes
  • Parallèle ? Demandez-vous d'abord : périmètres disjoints ? Sinon, séquentiel.
  • Contradiction ? Critère déterministe partagé, puis humain.
  • Bloqué ? Borne + escalade, jamais « relancer jusqu'à ce que ça passe ».

4 · Évaluation, analyse des erreurs et ajustement

Perform evaluation, error analysis, and tuning

15–20 % de l'examenFormation : chapitres 07, 10

Ce que dit le guide d'étude

CompétencePoints évalués
Critères de succès et signauxRésultats attendus et contraintes opérationnelles ; signaux qualitatifs et quantitatifs ; critères alignés sur l'intention ; signaux produits par des outils de scan automatiques.
Analyser les échecsTrouver les échecs dans les journaux, plans, traces, sorties et artefacts de workflow ; classer la cause racine : raisonnement, mauvais usage d'outil, contexte ou environnement.
AjusterRéviser instructions, workflows ou contraintes ; affiner l'usage de la mémoire ; affiner l'usage et l'accès aux outils.

Définir le succès avant de mesurer

ÉlémentExemple SprintDesk
Résultat attendu5 US du lot traitées : créée, modifiée, inchangée ou bloquée
Contraintes opérationnellesPas d'écriture hors sortie/ ; aucune ND-xx tranchée ; 59 min max pour une tâche cloud agent
Alignement sur l'intentionOn mesure « US exploitable et traçable », pas « nombre de lignes écrites »

Signaux

QuantitatifsQualitatifs
Checks verts / rouges ; nombre d'erreurs de verifier-us ; alertes de scan ; nombre d'itérations sur la PR ; taux de PR fusionnées ; délai jusqu'à la fusion ; US inchangées à tortClarté des critères d'acceptation ; pertinence des questions ouvertes ; respect des conventions ; qualité du plan ; jugement du relecteur

Signaux produits automatiquement

Ce que le cloud agent lance seul, sur son propre code (sans licence GitHub Advanced Security) :
  • CodeQL : problèmes de sécurité du code ;
  • GitHub Advisory Database : nouvelles dépendances avec avis de malware ou vulnérabilité CVSS élevée ou critique ;
  • Secret scanning : clés, jetons ;
  • Copilot code review : second avis.
Ces validations sont désactivables une par une dans les réglages du cloud agent. Le détail est dans le journal de session.

À ajouter soi-même : tests, linters, scripts métier (verifier-us.cjs) en checks requis ; Dependabot ; code scanning sur toutes les PR.

Où chercher les preuves

SourceCe qu'on y trouve

PlanCe qui était prévu : écart = dérive ou plan faux
Traces VS Code (vue de débogage du chat, références)Fichiers réellement lus, outils et arguments
SortiesLe résultat, comparé aux critères
Artefacts et journaux de workflow, check runs, résumé de jobPreuve objective : tests, scans, contrôles
Historique Git, PR, audit logQui, quand, quelle version d'agent

Classer la cause racine

CauseSignatureExempleAjustement
Raisonnement (reasoning error)Bonnes infos disponibles et lues, mauvaise conclusionA lu RM-05 et fixe quand même une prioritéPréciser la procédure, exemple et contre-exemple, découper la tâche
Mauvais usage d'outil (tool misuse)Mauvais outil, mauvais arguments, outil absent ou en tropÉcrit dans entree/ au lieu de sortie/ ; boucle de rechercheRetirer / ajouter l'outil, consigne d'usage, hook
Contexte (context issue)Information absente, ambiguë, contradictoire ou périméeregles-metier.md jamais lu ; deux instructions contradictoiresCiter la source, supprimer la contradiction, corriger la mémoire
Environnement (environment issue)Dépendance absente, pare-feu, droits, mauvais emplacement de fichierNode absent : hook en échec ; domaine bloqué par le pare-feucopilot-setup-steps, liste du pare-feu, chemin corrigé

Ajuster une chose à la fois

1 défaut → 1 cause → 1 modification → rejouer le même jeu d'essai → vérifier l'absence de régression
LevierExemple
Instructions / workflow / contraintesAjouter la condition d'arrêt « ND-xx rencontrée » ; rendre un check requis
MémoireSupprimer un fait erroné ; passer une règle en applyTo ; versionner le plan
Outils et accèsRetirer execute du reviewer ; MCP en lecture seule ; préinstaller une dépendance

Pièges

Les erreurs classiques
  • Faire confiance au résumé de l'agent (« tous les tests passent ») sans regarder les checks.
  • Corriger le prompt alors que la cause est l'environnement (dépendance absente, pare-feu).
  • Modifier plusieurs leviers en même temps : on ne sait plus ce qui a corrigé ou cassé.
  • Mesurer un indicateur facile mais non aligné (volume de code, nombre de fichiers).
  • Croire que les scans du cloud agent exigent une licence GHAS : non.

Trucs et astuces

Méthode express
  • Trois questions : qu'a-t-on donné à l'agent ? qu'a-t-il fait ? qu'attendait-on ?
  • « Il avait l'info et s'est trompé » = raisonnement. « Il n'avait pas l'info » = contexte. « Il ne pouvait pas » = outil ou environnement.
  • Rejouer aussi un cas qui marchait (US déjà correcte) pour détecter la régression.

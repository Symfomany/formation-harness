3 · Mémoire, état et exécution

Manage memory, state, and execution

10–15 % de l'examenFormation : chapitres 01, 07, 11

Ce que dit le guide d'étude

CompétencePoints évalués
Stratégies de mémoireChoisir entre mémoire court terme, long terme et externe ; limiter la mémoire à l'utile pour la tâche ; règles d'expiration, d'élagage (pruning) et de réinitialisation.
Persister l'état, gérer la dériveProgression et décisions en artefacts durables ; reprendre sans répéter ni contredire ; détecter et corriger la dérive pendant une longue exécution.
Continuité entre outils et environnementsPartager l'état ; éviter le contexte contradictoire ; éviter le contexte périmé (stale).

Les trois mémoires

TypeExemplesDurée de vieQuand la choisir
Court terme (short-term)Fenêtre de contexte de la session : messages, fichiers lus, résultats d'outilsLa session ; résumée automatiquement quand elle satureRaisonnement en cours, détails éphémères
Long terme (long-term)Copilot Memory ; fichiers d'instructions ; skillsPlusieurs sessionsConventions stables, faits durables sur le dépôt
Externe (external)Fichiers versionnés (plan, journal), issues, PR, données via MCPAussi longtemps que la sourceÉtat partagé, décisions à auditer, reprise par un autre agent ou humain

Copilot Memory : les faits à retenir

Copilot Memory
  • Deux familles : faits du dépôt (repository facts) et préférences de l'utilisateur.
  • Chaque fait du dépôt porte des citations (emplacements dans le code). Avant usage, Copilot les vérifie sur la branche courante : un fait contredit par le code n'est pas utilisé.
  • Expiration : 28 jours sans utilisation. Un fait validé et utilisé repart pour 28 jours.
  • Seuls les utilisateurs avec accès en écriture génèrent des faits du dépôt.
  • Copilot code review n'utilise que les faits du dépôt, pas les préférences personnelles.
  • Les propriétaires du dépôt voient et suppriment les faits ; les administrateurs peuvent exporter ou supprimer les préférences.

Fichiers d'instructions (mémoire long terme explicite)

FichierPortée
.github/copilot-instructions.mdTout le dépôt, toujours
.github/instructions/*.instructions.md + applyTo (glob)Fichiers ciblés uniquement : mémoire limitée à la tâche
AGENTS.md (et équivalents à la racine)Instructions pour agents ; lues par plusieurs outils
Skills (SKILL.md)Chargées seulement quand la tâche correspond : contexte économisé

Copilot code review ne lit que les 4 000 premiers caractères d'un fichier d'instructions. On peut exclure un fichier d'une surface avec excludeAgent (ex. "code-review").

Limiter, expirer, réinitialiser

RègleMise en œuvre
Limiter à l'utile (scope)applyTo, skills à la demande, sous-agents à contexte isolé, outils MCP en lecture ciblée
ExpirerCopilot Memory : 28 jours ; plan : numéro de version, plan périmé = plan à refaire
Élaguer (prune)Supprimer les faits faux dans les réglages ; archiver les vieux journaux ; CLI : /compact
Réinitialiser (reset)Nouvelle session ; CLI : /clear ; repartir des artefacts (plan + journal), pas de l'historique du chat

État durable et reprise

  • Capturer : plan versionné, journal d'exécution (étape, résultat, commit, décision humaine), une PR dont la description sert de liste de progression, un commit par étape.
  • Reprendre : relire plan + journal, repartir de la première étape non terminée ; CLI : --continue ou --resume ; cloud agent : @copilot dans la PR existante, qui continue sur la même branche.
  • Ne pas diverger : les décisions prises sont écrites (« ND-02 reste ouverte ») et rappelées au démarrage (hook sessionStart, source = resume).

Dérive, contexte contradictoire, contexte périmé

ProblèmeSignalRemède
Dérive (drift)L'agent oublie une contrainte après un long échange ; actions hors planContraintes dans des fichiers toujours chargés ; réinjection par hook ; comparer journal et plan ; session neuve
Contexte contradictoire (conflicting)copilot-instructions.md et AGENTS.md disent l'inverse ; deux agents avec des versions différentes du planUne seule source de vérité par règle ; supprimer les doublons ; état partagé dans le dépôt
Contexte périmé (stale)Mémoire qui cite du code supprimé ; plan v1 utilisé alors que v2 existeCitations vérifiées (Copilot Memory) ; versions ; expiration ; relire la source avant d'agir

Partager l'état entre VS Code, CLI et cloud agent : dans le dépôt (fichiers, branches, PR, issues). Une conversation de chat n'est pas un état partagé.

Exemple concret

Un groupe traite le lot 3 sur deux jours. Jour 1 : diagnostic validé, journal à jour, commit 3f2a9c1. Jour 2 : un collègue reprend dans la CLI.

  1. Il ne réutilise pas le chat de la veille. Il lit plan-lot3.md (v2, APPROUVÉ) et journal-lot3.md.
  2. Le hook sessionStart rappelle les ND-xx ouvertes.
  3. Il lance l'étape 2 uniquement. L'étape 1 n'est pas refaite.

Pièges

Les erreurs classiques
  • Croire que Copilot Memory garde un fait « pour toujours » : 28 jours sans usage, et il est vérifié contre la branche courante.
  • Utiliser la mémoire du chat pour un état que d'autres doivent reprendre : il faut un artefact externe.
  • Tout mettre dans copilot-instructions.md : contexte gonflé, règles diluées. Préférer applyTo et skills.
  • Croire qu'un long fichier d'instructions est intégralement lu par code review : 4 000 premiers caractères.
  • Résoudre la dérive en « répétant la règle dans le prompt » : solution fragile. Mieux : mécanisme (hook, check) + artefact.

Trucs et astuces

Lecture des questions
  • « Doit survivre à la session et être audité » → mémoire externe versionnée.
  • « Convention stable pour tout le dépôt » → instructions (long terme).
  • « Détail utile seulement pour cette étape » → court terme, ne pas persister.
  • « L'agent utilise une info obsolète » → réponse qui parle de citations, de vérification, d'expiration ou de suppression du fait.

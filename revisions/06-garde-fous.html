6 · Garde-fous et responsabilité

Implement guardrails and accountability

10–15 % de l'examenFormation : chapitres 10, 12

Ce que dit le guide d'étude

CompétencePoints évalués
Niveaux d'autonomieClasser les actions selon le risque opérationnel, de sécurité et de conformité ; attribuer des niveaux d'autonomie qui maximisent la vitesse en restant conforme (sécurité, IA responsable).
Garde-fous et humain dans la boucleIdentifier les actions qui exigent un jugement humain ; bloquer les actions contraires aux politiques ; moindre privilège ; autorisation explicite ou chemin contrôlé pour l'irréversible ; ne pas multiplier les approbations qui ne réduisent pas le risque.

Hooks : échec ouvert ou fermé

À savoir par cœur
  • preToolUse en commande qui plante ou sort avec un code non nul (dont 2) : refus (fail-closed).
  • Délai dépassé : autorisé (fail-open), quel que soit l'événement. Délai par défaut : 30 s.
  • Hook HTTP en erreur : autorisé.
  • Refus : permissionDecision: "deny" + permissionDecisionReason obligatoire.
  • agentStop / subagentStop : decision: "block" + reason ; garde-fou anti-boucle après 8 blocages ; stop_hook_active indique un tour déjà forcé.
  • Cloud agent : ask vaut deny ; seul bash / command est exécuté.

Moindre privilège

  • Workflows : permissions: au niveau du job, contents: read par défaut, écriture seulement dans le job qui en a besoin.
  • Agents : tools listés ; MCP : outils en lecture listés ; jetons limités au dépôt.
  • Secrets : seulement ceux nécessaires, de type Agents pour le cloud agent, secrets d'environnement pour le déploiement.
  • Entrées de workflow : passer par env:, jamais ${{ ... }} directement dans run: (injection de commande).
  • Actions tierces épinglées par SHA complet.

Garder la vitesse

Approuver moins, mais mieux
  • Pas d'approbation sur la lecture ni sur l'écriture en branche isolée : contrôles automatiques à la place.
  • Une approbation là où elle réduit un risque réel : fusion, déploiement, configuration des agents.
  • Les contrôles déterministes (hooks, checks) remplacent des relectures manuelles répétitives.
  • Regrouper les retours sur une PR en une seule revue.

Exemple concret

SprintDesk : le rédacteur peut écrire dans sortie/ (autonome). preToolUse refuse entree/, contexte/, git push. Le check « Politique - sources protégées » bloque une PR qui touche entree/. La publication passe par l'environnement publication avec approbateur et interdiction de s'auto-approuver. Les ND-xx restent des questions ouvertes.

Pièges

Les erreurs classiques
  • Un hook de sécurité lent : s'il dépasse le délai, l'action passe.
  • Répondre allow dans un hook de sécurité : on court-circuite l'approbation normale. Répondre {} quand on n'a pas d'objection.
  • Croire qu'un label suffit comme autorisation : un rôle triage peut poser des labels. La vraie barrière est la revue.
  • Choisir « approbation humaine de chaque commande » : non conforme à l'objectif de vitesse.
  • Donner contents: write au niveau du workflow entier.

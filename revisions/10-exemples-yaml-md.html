1 · Workflow de validation et protection de branche

Un workflow agent-validation, un CODEOWNERS et une protection de main. La question classique : pourquoi la fusion reste-t-elle bloquée ?

# Nom du workflow dans l'onglet Actions (le check requis porte le nom du JOB)
name: agent-validation

# Déclencheurs : les évènements qui démarrent le workflow
on:
  # Sur pull request : le code proposé est contrôlé avant fusion
  pull_request:
    # Filtre : branches cibles de la PR
    branches:
      # La branche protégée par le ruleset
      - main
  # File de fusion : sans ceci, le check requis ne tourne pas dans la merge queue
  merge_group:

# Droits du jeton GITHUB_TOKEN : moindre privilège (lecture par défaut)
permissions:
  # Lire le code uniquement, aucune écriture
  contents: read
  # Lire les PR (nécessaire à gh pr view)
  pull-requests: read

# Les jobs : unités de travail. Le NOM du job devient le nom du check
jobs:
  # Job « test » : c'est CE nom que le ruleset doit exiger (pas le nom du workflow)
  test:
    # Machine virtuelle hébergée qui exécute le job
    runs-on: ubuntu-latest
    # Étapes exécutées dans l'ordre
    steps:
      # Récupère le code du dépôt (sans ça, aucun fichier à tester)
      - uses: actions/checkout@v4
      # Installation reproductible depuis le lockfile
      - run: npm ci
      # Tests : une preuve, pas une approbation de fusion
      - run: npm test
# .github/CODEOWNERS
# Chemin sensible : la revue de cette équipe est exigée
/src/payments/ @octo-org/payments-reviewers
# Modifier un workflow = modifier la sécurité : revue plateforme
/.github/workflows/ @octo-org/platform-reviewers
Branch protection for main:
# Aucun push direct : tout passe par une PR
- Require pull request before merging: enabled
# Sans cette case, CODEOWNERS ne sert à rien
- Require review from Code Owners: enabled
# Les contrôles automatiques doivent être verts
- Require status checks before merging: enabled
# Nom du JOB à exiger (pas du workflow)
- Required check: agent-validation
Réponse : que se passe-t-il ?

Le check requis est agent-validation, qui est le nom du workflow. Or le contexte de statut publié est le nom du job : test. Le check requis n'est jamais rapporté, la fusion reste en attente. Corrections : requérir test, ou nommer le job agent-validation.

  • merge_group: est nécessaire pour que le check tourne aussi dans une file de fusion.
  • Un changement de .github/workflows/ exige la revue de platform-reviewers : un agent ne peut pas modifier sa propre validation sans eux.
  • contents: read + pull-requests: read : moindre privilège, aucune écriture.
Pièges
  • Nom du workflow ≠ nom du check : c'est le job (ou workflow / job pour les jobs à matrice) qui compte.
  • Des tests verts ne valent pas approbation : la revue des Code Owners reste exigée.
  • Sans merge_group, un check requis ne s'exécute pas sur la file de fusion.

# Rôle
Tu investigues un incident, proposes un correctif minimal et ajoutes un test de non-régression.

## Règles
- Lecture seule sur Sentry : ne jamais modifier ou résoudre une issue.

Réponse : quelle incohérence ?

L'agent déclare sentry/get_issue dans tools, mais le serveur n'expose que list_issues (tools: du serveur). get_issue n'est pas autorisé côté MCP : il faut l'ajouter dans la liste du serveur, ou le retirer de l'agent. La liste du serveur fait office de liste d'autorisation.

Autre point de vigilance : execute est large. Pour un agent d'incident, le restreindre ou le garder derrière des hooks preToolUse.

5 · CODEOWNERS sur .github/agents/** et check guardrail-policy-check

Les fichiers qui pilotent les agents (instructions, profils, MCP, workflows) sont de la chaîne d'approvisionnement : relus par des propriétaires dédiés, protégés par un check requis.

# .github/CODEOWNERS
# Instructions des agents : gouvernance IA
.github/copilot-instructions.md @octo-org/ai-governance
# Tous les profils d'agent (récursif) : l'agent ne valide pas son propre profil
.github/agents/** @octo-org/ai-governance
# Serveurs MCP : ajouter un serveur est une décision de sécurité
.github/mcp.json @octo-org/platform-security
# Tous les workflows, dont le contrôle lui-même
.github/workflows/** @octo-org/platform-security
Branch protection for main:
# Aucun push direct : tout passe par une PR
- Require pull request before merging: enabled
# Sans cette case, CODEOWNERS ne sert à rien
- Require review from Code Owners: enabled
# Les contrôles automatiques doivent être verts
- Require status checks before merging: enabled
# Nom du JOB à exiger (pas du workflow)
- Required check: guardrail-policy-check
# Même un administrateur passe par la PR : politique non contournable
- Allow bypassing required pull requests: disabled
# Nom du workflow dans l'onglet Actions (le check requis porte le nom du JOB)
name: guardrail-policy-check

# Déclencheurs : les évènements qui démarrent le workflow
on:
  # Sur pull request : le code proposé est contrôlé avant fusion
  pull_request:
    # Filtre : branches cibles de la PR
    branches:
      # La branche protégée par le ruleset
      - main
  # File de fusion : sans ceci, le check requis ne tourne pas dans la merge queue
  merge_group:

# Droits du jeton GITHUB_TOKEN : moindre privilège (lecture par défaut)
permissions:
  # Lire le code uniquement, aucune écriture
  contents: read

# Les jobs : unités de travail. Le NOM du job devient le nom du check
jobs:
  # Job = check requis : même nom que dans la protection de branche
  guardrail-policy-check:
    # Machine virtuelle hébergée qui exécute le job
    runs-on: ubuntu-latest
    # Étapes exécutées dans l'ordre
    steps:
      # Récupère le code du dépôt (sans ça, aucun fichier à tester)
      - uses: actions/checkout@v4

      # Chaque serveur MCP déclaré doit figurer dans la liste d'autorisation
      - name: MCP allowlist
        run: |
          # Liste les serveurs MCP déclarés dans mcp.json
          jq -r '.mcpServers | keys[]' .github/mcp.json | while read -r s; do
            # Vérifie que chaque serveur figure dans la liste d'autorisation
            jq -e --arg s "$s" 'index($s)' .github/mcp-allowlist.json >/dev/null \
              || { echo "Serveur MCP non autorisé : $s"; exit 1; }
          done

      # Aucun profil d'agent ne doit donner un outil d'écriture non listé
      - name: Agents must declare tools
        run: |
          # Parcourt tous les profils d'agent
          for f in .github/agents/*.agent.md; do
            # Refuse un profil sans liste d'outils explicite
            grep -q '^tools:' "$f" || { echo "tools manquant : $f"; exit 1; }
          done
Pourquoi chaque ligne compte
  • CODEOWNERS + « Require review from Code Owners » : sans la case, le fichier ne sert à rien.
  • Check requis : le contrôle automatique ne peut pas être ignoré ; son job porte le même nom que le check.
  • « Allow bypassing » désactivé : même un administrateur passe par la PR, sinon la politique est contournable.
  • Le workflow de contrôle est lui-même sous .github/workflows/** : protégé par platform-security.
Pièges
  • Un CODEOWNERS non couvert (.github/agents/** oublié) : l'agent peut modifier son propre profil avec une revue ordinaire.
  • Le contournement autorisé annule tout le reste.
  • Une équipe de propriétaires sans accès en écriture au dépôt n'est pas prise en compte.

6 · Politique de liste d'autorisation MCP

Deux niveaux : l'organisation décide quels serveurs sont permis (politique / registre) ; le dépôt déclare ceux qu'il utilise.

{
  "mcpServers": {
    "sentry": {
      "type": "http",
      "url": "https://mcp.example.internal/sentry",
      "tools": ["list_issues", "get_issue"]
    },
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/readonly",
      "tools": ["*"]
    }
  }
}
["sentry", "github"]
À savoir
  • Moindre privilège MCP : serveur en lecture seule + tools listés (pas de "*" pour un outil qui écrit).
  • Le registre MCP de l'organisation limite aux serveurs approuvés ; le dépôt ne peut pas en ajouter hors liste.
  • Un secret de serveur MCP du cloud agent : secret de type Agents, jamais en clair dans mcp.json.
  • Le fichier mcp.json a ses propres propriétaires (platform-security) : ajouter un serveur est une décision de sécurité.

7 · Copilot CLI : outil d'écriture refusé

# Autoriser la lecture et quelques commandes git précises, refuser l'écriture.
# Lecture des options (une seule commande, coupée par « \ » pour la lisibilité) :
#   copilot                          lance l'agent en ligne de commande
#   --allow-tool 'shell(git status)' autorise CETTE commande shell précise
#   --allow-tool 'shell(git diff)'   autorise aussi git diff, rien d'autre en git
#   --deny-tool 'write'              refuse tout outil d'écriture de fichiers
#   --deny-tool 'shell(git push)'    refuse le push : le refus l'emporte toujours sur un allow
copilot \
  --allow-tool 'shell(git status)' \
  --allow-tool 'shell(git diff)' \
  --deny-tool 'write' \
  --deny-tool 'shell(git push)'

# Refuser un outil MCP précis : format « serveur(outil) », ici l'outil qui résout une issue Sentry
copilot --deny-tool 'sentry(resolve_issue)'
  • Un refus (--deny-tool) l'emporte sur une autorisation (--allow-tool), même si --allow-all-tools est présent.
  • Pour un refus non contournable par l'utilisateur, passer par un hook de politique administrateur ou preToolUse : une option de ligne de commande se retire.
{
  "version": 1,
  "hooks": {
    "preToolUse": [
      { "type": "command", "bash": "./scripts/deny-write.sh", "timeoutSec": 10 }
    ]
  }
}
#!/usr/bin/env bash
# Entrée JSON sur stdin ; refuser tout écriture hors sortie/
# Lit tout le JSON envoyé par l'agent
input=$(cat)
# Nom de l'outil demandé (edit, bash...)
tool=$(echo "$input" | jq -r '.toolName')
# Chemin visé par l'écriture, vide sinon
path=$(echo "$input" | jq -r '.toolArgs.path // empty')

# Règle : écriture permise seulement dans sortie/
if [ "$tool" = "edit" ] && [[ "$path" != sortie/* ]]; then
  # Refus avec raison obligatoire
  echo '{"permissionDecision":"deny","permissionDecisionReason":"Écriture hors sortie/ interdite"}'
fi
# Pas d'objection : ne rien répondre (ou {}), jamais "allow"
Pièges
  • Répondre allow dans un hook de sécurité court-circuite l'approbation normale.
  • Hook trop lent : délai dépassé = autorisé (fail-open). Garder le script court.
  • Script qui plante ou sort non nul : refus (fail-closed).

8 · Journal multi-agents : lire un échec de passation

# Évènement qui a déclenché l'exécution
Event: pull_request
# Qui a agi : le bot Copilot
Actor: github-copilot[bot]

# Étape 1 : le planificateur décide, il n'implémente pas
Job: planner
Conclusion: success
Output:
  # Contrainte posée par le planificateur : le schéma ne doit pas changer
  decision = "Proceed only if schema remains unchanged"
Artifact:
  # Passation par artefact écrit, pas par conversation
  planner-handoff.md uploaded

# Étape 2 : l'implémenteur applique le plan
Job: implementer
Conclusion: success
Log:
  Changed files:
    src/orders/serializer.ts
    # INDICE : une migration = un changement de schéma
    db/migrations/20260526_add_order_state.sql
  Outcome note:
    # L'implémenteur déclare lui-même avoir changé le schéma
    "Added schema migration to support new state"

# Étape 3 : le réviseur compare plan et résultat
Job: reviewer
Conclusion: failure
Log:
  # Le réviseur lit la décision durable
  Loaded planner decision from planner-handoff.md
  # Le réviseur lit le résultat réel
  Loaded implementer outcome from implementation-summary.md
  # Contradiction détectée : le plan n'a pas été respecté
  ERROR: Handoff violation detected
  Planner decision forbids schema change, but implementer changed db/migrations/
Réponse : quelle est la cause ?

L'implémenteur a violé la contrainte du planificateur (pas de changement de schéma) : il a ajouté une migration. Le réviseur a bien fait son travail en comparant la décision durable (planner-handoff.md) au résultat (implementation-summary.md). L'échec n'est ni un bug du réviseur, ni un problème de permissions.

Fix : faire de la contrainte un mécanisme (check interdisant db/migrations/** tant que le plan ne l'autorise pas), et renvoyer à l'humain la décision « le schéma doit changer ».

Réflexes
  • Passation par artefact écrit, pas par la mémoire d'un agent.
  • Le réviseur lit les artefacts, pas les affirmations (« success » du job ne prouve pas la conformité).
  • Une contrainte qui conditionne la suite doit être vérifiable par un contrôle automatique.

9 · Cas d'usage concrets

Six situations réelles, avec un YAML complet et son explication juste en dessous.

Cas A · Bloquer une PR qui touche les sources protégées

# Nom du workflow dans l'onglet Actions (le check requis porte le nom du JOB)
name: Politique - sources protégées

# Déclencheurs : les évènements qui démarrent le workflow
on:
  # Sur pull request : le code proposé est contrôlé avant fusion
  pull_request:
    # Filtre : branches cibles de la PR
    branches:
      # La branche protégée par le ruleset
      - main

# Droits du jeton GITHUB_TOKEN : moindre privilège (lecture par défaut)
permissions:
  # Lire le code uniquement, aucune écriture
  contents: read
  # Lire les PR (nécessaire à gh pr view)
  pull-requests: read

# Les jobs : unités de travail. Le NOM du job devient le nom du check
jobs:
  # Job qui protège les données sources
  sources-protegees:
    # Machine virtuelle hébergée qui exécute le job
    runs-on: ubuntu-latest
    # Étapes exécutées dans l'ordre
    steps:
      # Récupère le code du dépôt (sans ça, aucun fichier à tester)
      - uses: actions/checkout@v4
        # Paramètres de l'action
        with:
          # Historique complet : nécessaire pour comparer deux commits
          fetch-depth: 0

      - name: Refuser toute modification de entree/ et contexte/
        # Variables d'environnement : entrées externes passées sans injection
        env:
          # Commit de base de la PR, passé par variable
          BASE_SHA: ${{ github.event.pull_request.base.sha }}
          # Dernier commit de la PR, passé par variable
          HEAD_SHA: ${{ github.event.pull_request.head.sha }}
        run: |
          # Liste des fichiers modifiés par la PR
          changed=$(git diff --name-only "$BASE_SHA" "$HEAD_SHA")
          # Cherche une modification dans un dossier interdit
          if echo "$changed" | grep -E '^(entree|contexte)/'; then
            # Annotation d'erreur visible directement dans la PR
            echo "::error::Les sources protégées ne sont pas modifiables par PR."
            # Échec du job : le check passe au rouge et bloque la fusion
            exit 1
          fi

Explication. L'agent peut écrire dans sortie/ mais jamais dans les données sources. Plutôt que de le demander dans une instruction, on l'impose : le job échoue si le diff touche entree/ ou contexte/. Une fois le job déclaré « check requis » dans le ruleset, la fusion est impossible. Les SHA passent par env: (pas d'injection) et les permissions restent en lecture. Réflexe d'examen : mécanisme > consigne.

          # Dossier conservé
          path: dist/

  # Job de publication : le seul à avoir des droits d'écriture
  publier:
    # Attend la réussite du build avant de publier
    needs: build
    # Machine virtuelle hébergée qui exécute le job
    runs-on: ubuntu-latest
    # Environnement protégé : approbateur humain requis avant le démarrage
    environment: publication
    # Droits du jeton GITHUB_TOKEN : moindre privilège (lecture par défaut)
    permissions:

      contents: read

      id-token: write

          # Nom de l'artefact
          name: site

Cas C · Rollback par revert, sans réécrire l'histoire

# Nom du workflow dans l'onglet Actions (le check requis porte le nom du JOB)
name: rollback

# Déclencheurs : les évènements qui démarrent le workflow
on:
  # Lancement manuel par un humain (pas d'exécution implicite)
  workflow_dispatch:
    # Paramètres saisis par l'opérateur au lancement
    inputs:
      # Paramètre « commit »
      commit:
        # Aide affichée à l'opérateur
        description: SHA du commit fusionné à annuler
        # Valeur obligatoire
        required: true

# Droits du jeton GITHUB_TOKEN : moindre privilège (lecture par défaut)
permissions:
  # ÉCRITURE du code : à confiner au job qui en a vraiment besoin
  contents: write
  # Écrire dans les PR (créer, commenter)
  pull-requests: write

# Les jobs : unités de travail. Le NOM du job devient le nom du check
jobs:
  # Job de retour arrière par revert
  revert:
    # Machine virtuelle hébergée qui exécute le job
    runs-on: ubuntu-latest
    # Environnement protégé : un humain valide le retour arrière
    environment: rollback
    # Variables d'environnement : entrées externes passées sans injection
    env:
      # Saisie utilisateur passée par variable, pas par ${{ }} dans run
      COMMIT: ${{ inputs.commit }}
      # Jeton pour la CLI gh, limité par permissions
      GH_TOKEN: ${{ github.token }}
    # Étapes exécutées dans l'ordre
    steps:
      # Récupère le code du dépôt (sans ça, aucun fichier à tester)
      - uses: actions/checkout@v4
        # Paramètres de l'action
        with:
          # Historique complet : nécessaire pour comparer deux commits
          fetch-depth: 0

      - name: Créer la branche de revert
        run: |
          # Identité du commit de revert : le bot (traçabilité)
          git config user.name "github-actions[bot]"
          # Adresse associée à l'identité du bot
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          # Crée une branche dédiée : on ne pousse jamais sur main
          git switch -c "revert/${COMMIT:0:7}"
          # Ajoute un commit qui annule l'autre (historique préservé)
          git revert --no-edit "$COMMIT"
          # Pousse la branche de revert (pas main)
          git push origin HEAD

      - name: Ouvrir la PR de revert
        run: |
          # Ouvre la PR de revert : checks et revue habituels
          gh pr create --base main --head "revert/${COMMIT:0:7}" \
            --title "Revert ${COMMIT:0:7}" \
            --body "Annulation du commit $COMMIT"

Explication. On annule avec git revert, qui ajoute un commit : l'historique est conservé, contrairement à reset --hard + push --force. Le revert passe par une PR, donc par les checks et la revue habituels, jamais par un push direct sur main. L'écriture est confinée à ce workflow, déclenché à la main, derrière l'environnement rollback. La saisie inputs.commit transite par env: pour éviter l'injection.

Cas E · Agents en parallèle sans conflit

# Nom du workflow dans l'onglet Actions (le check requis porte le nom du JOB)
name: lots-paralleles

# Déclencheurs : les évènements qui démarrent le workflow
on:
  # Lancement manuel par un humain (pas d'exécution implicite)
  workflow_dispatch:

# Droits du jeton GITHUB_TOKEN : moindre privilège (lecture par défaut)
permissions:
  # Lire le code uniquement, aucune écriture
  contents: read

# Les jobs : unités de travail. Le NOM du job devient le nom du check
jobs:
  # Un job par lot d'agent (matrice)
  lot:
    # Machine virtuelle hébergée qui exécute le job
    runs-on: ubuntu-latest
    # Coupe le job s'il boucle (agent ou test bloqué)
    timeout-minutes: 20
    # Stratégie d'exécution du job
    strategy:
      # Un lot en échec n'annule pas les autres (échec partiel)
      fail-fast: false
      # Matrice : un job par valeur
      matrix:
        # Trois lots, donc trois jobs en parallèle
        lot: [lot-1, lot-2, lot-3]
    # Évite deux exécutions simultanées du même groupe
    concurrency:
      # Clé d'exclusion : un groupe par lot
      group: ${{ matrix.lot }}
      # Ne pas annuler un lot en cours
      cancel-in-progress: false
    # Étapes exécutées dans l'ordre
    steps:
      # Récupère le code du dépôt (sans ça, aucun fichier à tester)
      - uses: actions/checkout@v4
      - name: Exécuter le lot
        # Exécute le lot courant
        run: ./scripts/executer-lot.sh "${{ matrix.lot }}"
      # Conserve le résultat comme artefact inspectable
      - uses: actions/upload-artifact@v4
        # S'exécute même si une étape précédente a échoué (preuve conservée)
        if: always()
        # Paramètres de l'action
        with:
          # Un artefact par lot : journal inspectable
          name: journal-${{ matrix.lot }}
          # Fichier de journal du lot
          path: journaux/${{ matrix.lot }}.md

  # Job d'agrégation des résultats de tous les lots
  consolider:
    # Attend les lots (avec if: always, même s'ils échouent)
    needs: lot
    # S'exécute même si une étape précédente a échoué (preuve conservée)
    if: always()
    # Machine virtuelle hébergée qui exécute le job
    runs-on: ubuntu-latest
    # Étapes exécutées dans l'ordre
    steps:
      # Récupère l'artefact produit plus tôt
      - uses: actions/download-artifact@v4
        # Paramètres de l'action
        with:
          # Récupère tous les journaux de lots
          pattern: journal-*
          # Les met dans un même dossier
          merge-multiple: true
      # Concatène en un bilan de consolidation
      - run: cat *.md > bilan.md

Explication. Chaque lot travaille sur son périmètre, indépendamment : matrix + concurrency par lot évitent les exécutions concurrentes d'un même lot. fail-fast: false gère l'échec partiel : un lot en erreur n'annule pas les autres. if: always() garantit que le journal de chaque lot est téléversé même en cas d'échec (observabilité, reprise). Le job consolider agrège les artefacts et tourne même si un lot a échoué, pour que l'humain voie l'état réel. timeout-minutes borne les agents qui bouclent.

11 · Trucs et astuces

La boîte à outils pour répondre vite et juste. Les réflexes de l'accueil, mais déclinés par thème, avec les mots-clés à repérer, la méthode d'élimination et les chiffres à connaître.

Les 20 réflexes généraux

Quand vous hésitez, choisissez celle qui…
  1. Impose par ruleset, check requis, hook, permission ou environnement plutôt que par une phrase d'instruction.
  2. Retire la capacité (outil non listé, jeton en lecture) plutôt que de demander poliment de ne pas l'utiliser.
  3. Garde un humain sur l'irréversible : fusion, déploiement, suppression, secrets, droits.
  4. Ne met pas d'humain ailleurs : une approbation qui ne réduit aucun risque est une mauvaise réponse.
  5. Laisse une trace durable : plan, PR, commit signé, journal, artefact.
  6. S'appuie sur des preuves : CI, scan, journal, jamais l'affirmation de l'agent.
  7. Annule sans réécrire l'histoire : revert, redéploiement d'un SHA sain.
  8. Traite la cause racine, une chose à la fois.
  9. Isole : une branche, un périmètre, un environnement par agent ou par lot.
  10. Est la plus simple qui satisfait toutes les contraintes : pas d'architecture plus lourde que le besoin.
  11. Passe par un chemin contrôlé (PR, environnement protégé) plutôt que par un contournement.
  12. Est automatique et déterministe pour le répétitif (hook, check) et humaine pour le jugement.
  13. Échoue fermé : en cas de doute, refuser.
  14. Sépare les rôles : qui écrit n'est pas qui approuve, qui planifie n'est pas qui exécute.
  15. Traite toute entrée externe comme non fiable : issue, titre de PR, sortie d'outil, page web.
  16. Limite le rayon d'action d'une erreur : petit lot, brouillon, branche jetable.
  17. Garde la vitesse : autonomie sur le faible risque, contrôles automatiques.
  18. Documente la décision là où elle sera retrouvée : PR, PLAN.md, journal.
  19. Vérifie l'état réel avant d'agir (idempotence, contexte frais), jamais sur une mémoire périmée.
  20. Escalade quand c'est irréversible, ambigu ou après des échecs répétés, pas systématiquement.

Méthode d'élimination

En 5 passes sur un QCM
  1. Éliminez les extrêmes : « toujours », « jamais », « tous », « aucun » sont rarement justes.
  2. Éliminez les réponses qui élargissent les droits (write partout, bypass, désactiver un check).
  3. Éliminez celles qui ralentissent sans réduire de risque (approuver chaque commande).
  4. Éliminez celles qui ne laissent pas de trace ou reposent sur la mémoire de l'agent.
  5. Entre les deux restantes, prenez celle qui impose plutôt que demande.
Questions « Select all »
  • Évaluez chaque proposition indépendamment : vraie ou fausse, sans les comparer.
  • Comptez le nombre de réponses demandé s'il est indiqué.
  • Une proposition juste mais hors sujet reste fausse pour la question posée.
Questions « Missing value »
  • Repérez la syntaxe exacte : run:, uses:, permissions, nom de job imposé.
  • Les noms imposés sont des classiques : copilot-setup-steps, ready_for_review, .agent.md, copilot-instructions.md.
  • Le type de valeur vous guide : un booléen, un nom d'action, une commande shell.

# Nom affiché dans l'onglet Actions (≠ nom du check, qui vient du job)
name: ci-agent

# Quand le workflow se déclenche
on:
  # Sur chaque PR dont la cible est main
  pull_request:
    branches:
      - main
    # Ces types couvrent ouverture, nouveaux commits et passage en « prête »
    types:
      - opened
      - synchronize
      - ready_for_review
  # Indispensable pour que le check s'exécute aussi dans la file de fusion
  merge_group:

# Droits par défaut du jeton pour TOUS les jobs : lecture seule
permissions:
  contents: read

# Évite deux exécutions simultanées pour la même PR
concurrency:
  # Un groupe par workflow et par référence (branche de la PR)
  group: ci-agent-${{ github.ref }}
  # Une nouvelle exécution annule l'ancienne devenue inutile
  cancel-in-progress: true

jobs:
  # Le nom de CE job est le nom du check à exiger dans le ruleset
  verifier:
    # Machine virtuelle hébergée par GitHub
    runs-on: ubuntu-latest
    # Coupe le job s'il boucle (agent ou test bloqué)
    timeout-minutes: 15
    steps:
      # Récupère le code de la PR (action officielle)
      - uses: actions/checkout@v4

      # Installe Node et active le cache des dépendances
      - uses: actions/setup-node@v4
        with:
          # Version imposée : même environnement qu'en local
          node-version: "20"
          # Accélère les exécutions suivantes
          cache: npm

      # Installation reproductible depuis le lockfile (échoue s'il diverge)
      - run: npm ci

      # Analyse statique : détecte les erreurs avant les tests
      - run: npm run lint

      # Tests : une preuve, pas une approbation
      - run: npm test

      # Audit des dépendances : échoue à partir du niveau « high »
      - run: npm audit --audit-level=high

      # Étape nommée pour être lisible dans les journaux
      - name: Vérifier la présence du plan
        # Entrée externe passée par env (anti-injection)
        env:
          PR_BRANCH: ${{ github.head_ref }}
        # Bloc shell multiligne
        run: |
          # Le plan doit exister, sinon la PR est refusée
          test -f .github/agent-plans/implementation-plan.md
          # Il doit contenir la section « Rollback »
          grep -q "## Rollback" .github/agent-plans/implementation-plan.md

          echo "Plan présent pour la branche $PR_BRANCH"

Cas J · Script de hook preToolUse

#!/usr/bin/env bash
# Interpréteur : bash, pour utiliser [[ ]] et les tableaux
set -euo pipefail
# -e : s'arrête à la première erreur (un plantage = refus, fail-closed)
# -u : variable non définie = erreur
# -o pipefail : une erreur dans un pipe n'est pas masquée

# Lit tout le JSON envoyé par l'agent sur l'entrée standard
input=$(cat)

# Extrait le nom de l'outil demandé (ex. bash, edit)
tool=$(echo "$input" | jq -r '.toolName')

# Extrait la commande shell, vide si ce n'est pas un appel bash
cmd=$(echo "$input" | jq -r '.toolArgs.command // empty')

# Extrait le chemin visé par une édition, vide sinon
path=$(echo "$input" | jq -r '.toolArgs.path // empty')

# Fonction : écrit la décision de refus au format attendu
deny() {
  # Doit contenir decision ET raison (la raison est obligatoire)
  printf '{"permissionDecision":"deny","permissionDecisionReason":"%s"}\n' "$1"
  # Sortie 0 : la réponse JSON est lue normalement
  exit 0
}

# Règle 1 : jamais de push depuis l'agent
if [[ "$tool" == "bash" && "$cmd" == *"git push"* ]]; then
  deny "git push interdit : passer par la PR"
fi

# Règle 2 : jamais de suppression récursive
if [[ "$tool" == "bash" && "$cmd" == *"rm -rf"* ]]; then
  deny "Suppression récursive interdite"
fi

# Règle 3 : écriture autorisée seulement dans sortie/
if [[ "$tool" == "edit" && "$path" != sortie/* ]]; then
  deny "Écriture hors sortie/ interdite"
fi

# Aucune objection : réponse vide, on laisse l'approbation normale décider
echo '{}'

Ce qu'il faut retenir. Le script lit une entrée, applique des règles déterministes et ne renvoie jamais allow. Il doit rester rapide (délai dépassé = autorisé). Une erreur de script = refus.

Cas K · Déploiement avec contrôle de santé et rollback

name: deploy-prod

# Déclenché à la main uniquement : pas de déploiement implicite
on:
  workflow_dispatch:
    # Paramètre saisi par l'opérateur
    inputs:
      version:
        description: Tag ou SHA à déployer
        required: true

# Lecture seule par défaut
permissions:
  contents: read

# Un seul déploiement à la fois, sans annulation en cours
concurrency:
  group: deploy-prod
  cancel-in-progress: false

jobs:
  deployer:
    runs-on: ubuntu-latest
    # Environnement protégé : approbateur humain avant que le job démarre
    environment: production
    # Variables d'entrée sûres (jamais ${{ }} dans run)
    env:
      VERSION: ${{ inputs.version }}
      # Secret propre à l'environnement production
      DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
    steps:
      # Récupère exactement la version demandée
      - uses: actions/checkout@v4
        with:
          ref: ${{ inputs.version }}

      # Publie la version
      - name: Déployer
        run: ./scripts/deploy.sh "$VERSION"

      # Contrôle de santé : une preuve que le service répond
      - name: Vérifier la santé
        id: sante
        run: |
          # 10 tentatives espacées de 6 s (retry borné)
          for i in $(seq 1 10); do
            # -f : échec si code HTTP >= 400
            curl -fsS https://app.example.com/health && exit 0
            sleep 6
          done
          # Après 10 échecs : le step échoue
          exit 1

      # Ne s'exécute que si une étape précédente a échoué
      - name: Rollback vers la version saine
        if: failure()
        # Redéploie le dernier SHA connu sain (pas de reset ni de force-push)
        run: ./scripts/deploy.sh "$(cat .last-good-sha)"

Ce qu'il faut retenir. L'humain intervient à un seul endroit (l'environnement), le reste est automatique : déploiement, preuve de santé, retour arrière. Retry borné, secret isolé, aucune réécriture d'historique.

Cas L · Porte de PR : issue liée et commits signés

name: pr-gate

on:
  pull_request:
    branches:
      - main

# Lecture des PR nécessaire pour interroger l'API
permissions:
  contents: read
  pull-requests: read

jobs:
  # Check requis : nom du job
  pr-gate:
    runs-on: ubuntu-latest
    env:
      # Jeton fourni par GitHub, limité par les permissions ci-dessus
      GH_TOKEN: ${{ github.token }}
      # Numéro de PR transmis comme variable (pas d'injection)
      PR_NUMBER: ${{ github.event.pull_request.number }}
      # Dépôt courant (propriétaire/nom)
      REPO: ${{ github.repository }}
    steps:
      # Vérifie que la PR référence une issue (traçabilité du besoin)
      - name: Issue liée
        run: |
          # Récupère le corps de la PR au format brut
          body=$(gh pr view "$PR_NUMBER" --repo "$REPO" --json body -q .body)
          # Cherche « Closes #123 » ou « Fixes #123 »
          echo "$body" | grep -Eiq '(closes|fixes|resolves) #[0-9]+' \
            || { echo "::error::Aucune issue liée (Closes #N)"; exit 1; }

      # Vérifie que tous les commits sont signés (auteur vérifié)
      - name: Commits signés
        run: |
          # Liste les commits de la PR avec leur statut de vérification
          unsigned=$(gh api "repos/$REPO/pulls/$PR_NUMBER/commits" \
            --jq '[.[] | select(.commit.verification.verified == false)] | length')
          # Échoue si au moins un commit n'est pas vérifié
          [ "$unsigned" -eq 0 ] \
            || { echo "::error::$unsigned commit(s) non signé(s)"; exit 1; }

      # Vérifie qu'aucun fichier sensible n'est touché sans revue dédiée
      - name: Fichiers de gouvernance
        run: |
          # Fichiers modifiés par la PR
          files=$(gh pr view "$PR_NUMBER" --repo "$REPO" --json files -q '.files[].path')
          # Si un fichier d'agent ou de workflow change, on le signale
          if echo "$files" | grep -Eq '^\.github/(agents|workflows)/'; then
            echo "::notice::Gouvernance modifiée : revue des Code Owners obligatoire"
          fi

Ce qu'il faut retenir. Trois preuves automatiques : besoin (issue), auteur (commits signés), gouvernance (CODEOWNERS). Aucune ne remplace la revue humaine : elles la rendent plus rapide et plus fiable.

Scénarios d'examen

Quatre-vingt-treize situations concrètes, au format des examens blancs : mémoire, contrôles de politique, relecteurs, workflow multi-agents, workflow de rollback, workflow « les tests passent », PR de déploiement générée par Copilot, rollback par SHA.

Répondre avant d'ouvrir la correctionChaque correction : réponse, pourquoi, piège
Méthode pour chaque cas
  1. Identifier le domaine et le risque réel.
  2. Éliminer les réponses qui reposent sur une consigne, un souvenir de l'agent ou une approbation inutile.
  3. Choisir le mécanisme qui impose, avec le moindre privilège et une trace.

Mémoire

Cas 1 · Un fait mémorisé est devenu faux

Après une refonte, Copilot code review continue de recommander l'ancienne convention de journalisation, mémorisée comme fait du dépôt. Que faire en premier ?

  • A. Ajouter « ignore ta mémoire » dans copilot-instructions.md
  • B. Supprimer le fait erroné dans les réglages Copilot Memory du dépôt, et documenter la nouvelle convention dans les instructions
  • C. Désactiver Copilot code review
  • D. Attendre 28 jours que le fait expire
Correction

B. Les propriétaires du dépôt peuvent supprimer un fait. Écrire la convention dans les instructions évite qu'elle soit réapprise à tort.

Piège : D est vrai en théorie (28 jours sans usage), mais le fait est justement utilisé, donc son délai repart. Et attendre n'est pas une correction.

Cas 2 · Une migration sur plusieurs jours et plusieurs outils

Une migration dure trois jours. Elle passe de VS Code à la CLI, puis au cloud agent. Les décisions doivent être reprises sans être rediscutées, et auditées. Quelle mémoire ?

  • A. Copilot Memory
  • B. Une longue session de chat jamais fermée
  • C. Un plan et un journal versionnés dans le dépôt (ou la description de la PR)
  • D. Les préférences personnelles de l'utilisateur
Correction

C. Mémoire externe, durable, partagée par tous les outils, auditable.

Piège : A semble séduisant, mais Copilot Memory est inférée par Copilot, expire et n'est pas un registre de décisions. B est résumée automatiquement et non partageable.

Cas 3 · La préférence personnelle ignorée en revue

Une développeuse a une préférence mémorisée (« tests en style Given/When/Then »). Copilot code review ne l'applique pas sur ses PR. Pourquoi ?

Correction

Copilot code review n'utilise que les faits du dépôt, pas les préférences personnelles. Pour une règle d'équipe : fichier d'instructions (applyTo sur les tests), en gardant à l'esprit que code review ne lit que les 4 000 premiers caractères.

Contrôles de politique

Cas 4 · Le check requis reste « en attente »

Le check « Tests » est requis par un ruleset. Une PR qui ne modifie que la documentation est bloquée : le check reste Expected — Waiting for status to be reported. Cause ?

  • A. Le runner est saturé
  • B. Le workflow a un filtre paths : il ne démarre pas, le statut n'arrive jamais
  • C. Copilot n'a pas approuvé la PR
  • D. Il manque contents: write
Correction

B. Retirer le filtre paths du workflow requis, ou filtrer à l'intérieur du job (un job qui se termine en succès reste un statut).

Piège : un job sauté par une condition rapporte un succès ; un workflow jamais déclenché ne rapporte rien.

Cas 5 · Empêcher un agent de modifier les workflows

Vous voulez qu'aucune modification de .github/workflows/ ne soit fusionnée sans l'équipe plateforme, qu'elle vienne d'un agent ou d'un humain. Quelles mesures imposent cette règle ? (deux réponses)

  • A. Une phrase dans copilot-instructions.md
  • B. CODEOWNERS sur .github/workflows/ + ruleset « Require review from Code Owners »
  • C. Un ruleset qui exige une PR et bloque le push direct et le push forcé sur la branche par défaut
  • D. Demander à Copilot code review de surveiller ces fichiers
Correction

B et C. Un hook preToolUse peut s'ajouter en défense en profondeur côté agent.

Piège : A et D guident ou commentent, ils n'empêchent rien.

Cas 6 · N'autoriser que des serveurs MCP approuvés

L'entreprise veut que les développeurs n'utilisent que des serveurs MCP validés par la sécurité. Que configurer ?

Correction

Un registre MCP contenant les serveurs approuvés, et la politique Registry only au niveau organisation ou entreprise (au lieu de Allow all). Côté cloud agent : liste tools explicite et secrets COPILOT_MCP_.

Piège : désactiver complètement MCP « par sécurité » bloque aussi les usages légitimes : réponse trop large.

Relecteurs

Cas 7 · « Je ne peux pas approuver ma PR »

Paul a assigné une issue à Copilot. La PR est prête, Paul est le seul relecteur de l'équipe ce jour-là, le bouton d'approbation est inopérant. Pourquoi, et que faire ?

Correction

Celui qui a demandé la tâche au cloud agent ne peut pas approuver la PR : cela préserve la règle « approbations requises ». Il faut un autre relecteur. Si la PR n'est attribuée à personne (ouverte sous l'identité de l'application), une approbation supplémentaire est exigée.

Piège : contourner via un bypass ou en désactivant la règle.

Cas 8 · La revue de Copilot compte-t-elle ?

Le ruleset exige 1 approbation. Copilot code review a relu la PR sans rien trouver. La PR peut-elle être fusionnée ?

Correction

Non. Copilot code review laisse une revue de type Comment, jamais Approve ni Request changes. Elle ne compte pas dans les approbations requises.

Workflow multi-agents

Cas 9 · Deux agents, un même fichier

Deux issues sont assignées en parallèle au cloud agent. Les deux PR modifient config/routes.ts et entrent en conflit. Quelle est la meilleure prévention pour la suite ?

  • A. Lancer plus d'agents pour finir plus vite
  • B. Découper les tâches par périmètres de fichiers disjoints, ou séquencer celles qui touchent la même zone
  • C. Laisser le second agent forcer sa version
  • D. Fusionner les deux PR sans revue pour éviter le conflit
Correction

B. Résolution immédiate : fusionner la première, puis mettre à jour la seconde sur la base à jour (par exemple en demandant à @copilot de résoudre le conflit) et la relire.

Cas 10 · Deux agents se contredisent

Le reviewer déclare US-204 conforme ; le contrôleur la déclare non conforme. L'orchestrateur propose de garder l'avis majoritaire de trois agents.

Correction

Mauvaise idée. Bonne réponse : critère déterministe commun (ici verifier-us.cjs), puis arbitrage humain si le désaccord porte sur le fond. Documenter la décision dans le journal.

Cas 11 · L'orchestrateur tourne en rond

Un schéma producteur-critique tourne depuis 40 minutes : le critique refuse, le producteur reformule, sans fin.

Correction

Exécution bloquée. Borner le nombre de tours (2 ou 3), puis escalader à un humain avec les deux versions et la raison du refus. Côté hooks : le blocage de fin (agentStop) est limité à 8 fois, et stop_hook_active doit être respecté.

Workflow « les tests passent »

Cas 12 · « Tous les tests passent », dit l'agent

La PR du cloud agent indique « tous les tests passent ». Aucun check n'apparaît dans l'onglet des checks.

  • A. Fusionner : l'agent a lancé les tests
  • B. Relire le code, puis cliquer Approve and run workflows ; fusionner seulement si les checks requis sont verts
  • C. Demander à l'agent de relancer les tests
  • D. Désactiver les checks requis pour cette PR
Correction

B. Par défaut, les workflows ne tournent pas sur le code du cloud agent tant qu'un utilisateur avec accès en écriture ne les a pas approuvés. La preuve, c'est le check, pas la phrase de l'agent.

Cas 13 · L'agent ne peut pas lancer les tests

Le journal de session montre que l'agent n'arrive pas à installer les dépendances : délai réseau sur un registre interne.

Correction

Cause d'environnement. Préinstaller les dépendances dans copilot-setup-steps.yml (job copilot-setup-steps, branche par défaut), et/ou ajouter le registre à la liste autorisée du pare-feu. Ne pas réécrire le prompt : ce n'est pas un problème de raisonnement.

PR de déploiement générée par Copilot

Cas 14 · Copilot modifie le workflow de déploiement

Le cloud agent ouvre une PR qui modifie deploy.yml pour ajouter une étape. Quelles protections doivent jouer avant qu'un déploiement en production ait lieu ? (trois réponses)

  • A. Revue obligatoire des propriétaires de .github/workflows/ (CODEOWNERS)
  • B. Relire le diff avant « Approve and run workflows », car le workflow modifié s'exécuterait avec les droits du dépôt
  • C. Environnement production avec approbateurs, auto-approbation interdite, branche main seulement
  • D. Laisser Copilot fusionner après les checks verts
Correction

A, B et C. D est impossible : le cloud agent ne fusionne jamais.

Piège : cliquer « Approve and run workflows » sans relire, c'est exécuter du code de workflow non relu.

Cas 15 · Le déploiement casse la production

La PR de Copilot a été fusionnée et déployée. La production est en erreur. Que faire en premier ?

  • A. git reset --hard sur main puis push --force
  • B. Relancer le déploiement avec le SHA du dernier déploiement sain (approbation de l'environnement), puis ouvrir une PR de git revert
  • C. Demander à Copilot de corriger directement en production
  • D. Supprimer l'environnement
Correction

B. D'abord restaurer le service avec un état connu (SHA visible dans l'historique de déploiement), ensuite corriger l'historique proprement par revert et PR.

Workflow de rollback et rollback par SHA

Cas 16 · La PR de rollback n'a pas de checks

Le workflow de rollback crée une PR avec GITHUB_TOKEN. Les checks requis restent en attente, aucun workflow pull_request ne démarre.

Correction

Les événements créés avec GITHUB_TOKEN ne déclenchent pas de nouveaux workflows (sauf workflow_dispatch et repository_dispatch). Solutions : jeton d'une GitHub App dédiée, ou action humaine (commit, fermer/rouvrir). Pré-requis pour créer la PR : réglage « Allow GitHub Actions to create and approve pull requests ».

Cas 17 · Annuler un commit de fusion

Le SHA à annuler est un commit de fusion. Quelle commande ?

  • A. git reset --hard <sha>~1
  • B. git revert <sha>
  • C. git revert -m 1 <sha>
  • D. git cherry-pick <sha>
Correction

C. -m 1 indique de garder le premier parent (la branche cible). B échoue sur un commit de fusion. A réécrit l'historique.

Cas 18 · Le SHA saisi dans le formulaire

Un workflow de rollback contient : run: git revert ${{ inputs.sha }}. Quel est le risque, et la correction ?

Correction

Injection de commande : l'expression est remplacée avant l'exécution du shell. Correction : passer par env: SHA: ${{ inputs.sha }}, utiliser "$SHA", valider le format (40 caractères hexadécimaux) et vérifier que le commit appartient à la branche par défaut.

Garde-fous

Cas 19 · Le hook de sécurité laisse passer

Un hook preToolUse scanne tout le dépôt avant chaque écriture. Sur un gros dépôt, il met 45 s. Les écritures interdites passent. Pourquoi ?

Correction

Délai par défaut de 30 s dépassé : un timeout est toujours fail-open. Rendre le hook rapide (ne regarder que l'outil et le chemin), ajuster timeoutSec raisonnablement. Un plantage ou un code de sortie non nul, lui, refuse.

Cas 20 · Trop d'approbations

L'équipe exige une approbation manuelle pour chaque commande terminal de l'agent, y compris ls et git status. Les livraisons ralentissent. Meilleure réponse ?

  • A. Tout approuver automatiquement
  • B. Approuver automatiquement les commandes en lecture, refuser les commandes dangereuses par hook, garder l'humain sur fusion et déploiement
  • C. Interdire le terminal à l'agent
  • D. Garder la règle actuelle
Correction

B. Le guide demande de « minimiser les approbations qui ne réduisent pas le risque de façon significative ».

Scénarios supplémentaires

Trente-trois cas de plus, par domaine. Chaque correction explique chaque option : pourquoi elle est juste ou fausse.

Domaine 1 · Architecture et SDLC

Cas 21 · Aucun plan avant le code

Un agent reçoit une issue « Ajouter l'export CSV » et ouvre directement une PR de 40 fichiers. La revue est pénible : on ne sait pas ce qui était prévu. Quelle amélioration traite la cause ?

  • A. Demander des PR plus petites dans les instructions
  • B. Exiger un plan écrit (scope, fichiers, risques, tests, rollback) avant l'implémentation, vérifié par un check
  • C. Interdire à l'agent d'ouvrir des PR
  • D. Ajouter un second agent qui réécrit la PR
Correction

B. Le plan est un artefact inspectable : on compare le résultat à ce qui était prévu, et un check peut vérifier sa présence.

  • A ✗ consigne sans contrôle, et n'apporte pas de référence de comparaison.
  • C ✗ supprime la valeur de l'agent au lieu de traiter la cause.
  • D ✗ ajoute de la complexité sans trace ni critère.

Piège : « PR plus petites » est une bonne pratique, mais ne répond pas à « qu'était-il prévu ? ».

Cas 22 · Étape sans sortie définie

Votre chaîne : « analyse → plan → code → test ». L'étape « analyse » produit seulement une conversation. Le plan est régulièrement incohérent avec l'analyse. Que corriger ?

  • A. Choisir un modèle plus grand
  • B. Faire produire à chaque étape un artefact écrit (fichier d'analyse) qui sert d'entrée à la suivante
  • C. Supprimer l'étape d'analyse
  • D. Demander à l'humain de tout relire à chaque étape
Correction

B. Entrées/sorties explicites : l'étape suivante lit un contenu fixe, vérifiable et reprenable.

  • A ✗ un modèle plus puissant n'aide pas si l'information n'est pas transmise.
  • C ✗ perd l'étape utile.
  • D ✗ approbation systématique : lente et pas ciblée.

Piège : la cause est la passation, pas la capacité du modèle.

Cas 23 · Choisir le niveau d'autonomie

Associez l'autonomie la plus adaptée : (1) lire les issues, (2) pousser sur copilot/x, (3) fusionner dans main, (4) supprimer un secret. Quelle série est correcte ?

  • A. (1) humain · (2) humain · (3) autonome · (4) autonome
  • B. (1) autonome · (2) autonome avec contrôles · (3) humain · (4) humain seul
  • C. (1) autonome · (2) autonome · (3) autonome · (4) humain
  • D. Tout humain
Correction

B. L'autonomie suit le risque : faible = libre, moyen = contrôles automatiques, élevé/critique = humain.

  • A ✗ inverse la logique.
  • C ✗ laisse la fusion à l'agent.
  • D ✗ tue la vitesse sans réduire le risque.
Cas 24 · Décision métier ambiguë

L'issue dit « appliquer la remise fidélité ». Deux règles métier se contredisent dans la documentation. Que doit faire l'agent ?

  • A. Choisir la plus récente
  • B. Implémenter les deux sous feature flag
  • C. Signaler le conflit et poser une question ouverte à un humain, sans trancher
  • D. Appliquer la règle la plus simple à coder
Correction

C. Une décision métier ou de conformité n'appartient pas à l'agent.

  • A et D ✗ trancher sans mandat.
  • B ✗ double le travail et repousse la décision.
Cas 25 · Un seul agent fait tout

Un agent unique planifie, code, lance les tests et déclare « prêt ». Quel est le principal risque architectural ?

  • A. Coût élevé
  • B. Aucune séparation planifier / raisonner / agir : il valide son propre travail, sans point de contrôle indépendant
  • C. Trop de contexte
  • D. Trop de branches
Correction

B. Sans séparation, les erreurs s'enchaînent et rien n'est vérifié de l'extérieur.

  • A et C ✗ réels mais secondaires : la question demande le risque d'architecture.
  • D ✗ sans rapport.

Domaine 2 · Outils, MCP et environnements

Cas 26 · Outil MCP refusé alors qu'il est dans le profil

Le profil de l'agent liste sentry/get_issue, mais l'appel échoue. Le serveur déclare tools: [list_issues]. Quelle correction ?

  • A. Passer tools du serveur à ["*"]
  • B. Ajouter get_issue à la liste du serveur (si l'outil est en lecture seule) ou le retirer du profil
  • C. Redémarrer l'agent
  • D. Donner contents: write
Correction

B. Les deux listes doivent être cohérentes ; la liste du serveur est une liste d'autorisation.

  • A ✗ ouvre tous les outils, y compris ceux qui écrivent.
  • C ✗ ne change pas la configuration.
  • D ✗ sans rapport : c'est un droit de dépôt.
Cas 27 · L'environnement du cloud agent ne se prépare plus

Après un refactoring, le job de copilot-setup-steps.yml a été renommé setup. L'agent n'a plus ses dépendances, sans erreur. Cause ?

  • A. Le job doit s'appeler exactement copilot-setup-steps
  • B. ubuntu-latest n'est plus supporté
  • C. Il manque contents: write
  • D. Il faut un secret de type Agents
Correction

A. Le nom du job est un contrat avec Copilot.

  • B ✗ inventé.
  • C ✗ la préparation n'a besoin que de contents: read.
  • D ✗ les secrets servent à autre chose.
Cas 28 · Une clé d'API dans le dépôt

Un développeur a écrit la clé d'API d'un serveur MCP directement dans mcp.json. Que faire ?

  • A. Supprimer la ligne et continuer
  • B. Révoquer la clé, la stocker comme secret de type Agents, la référencer par nom ; activer le secret scanning et la protection push
  • C. Chiffrer la clé en base64
  • D. Mettre le dépôt en privé
Correction

B. Une clé committée est compromise : on la révoque, on la remplace et on empêche la récidive.

  • A ✗ la clé reste dans l'historique.
  • C ✗ base64 n'est pas du chiffrement.
  • D ✗ réduit l'exposition, ne l'élimine pas.
Cas 29 · Titre de PR dans un run:

Un workflow contient run: echo "${{ github.event.pull_request.title }}". Quel est le risque et la correction ?

  • A. Aucun risque, c'est un simple écho
  • B. Injection de commande ; passer le titre par env: et l'utiliser comme variable shell
  • C. Risque de coût ; limiter la durée
  • D. Risque de conflit ; ajouter concurrency
Correction

B. L'expression est remplacée avant l'exécution du shell : un titre contenant "; commande # s'exécute.

  • A ✗ faux : le titre est contrôlé par un tiers.
  • C et D ✗ ne concernent pas l'injection.
Cas 30 · pull_request_target avec checkout de la PR

Un workflow en pull_request_target fait checkout du code de la PR externe puis npm test, avec des secrets disponibles. Problème ?

  • A. Aucun
  • B. Du code non fiable s'exécute avec des secrets et des droits élevés : à éviter, ou ne jamais exécuter le code de la PR
  • C. Trop lent
  • D. Il faut ajouter fail-fast
Correction

B. Ce déclencheur s'exécute dans le contexte de la branche de base, avec secrets ; y lancer le code d'un tiers l'expose.

  • A ✗ sous-estime le risque.
  • C et D ✗ hors sujet.
Cas 31 · L'agent ne joint pas un registre de paquets

Le cloud agent échoue à télécharger des dépendances : hôte bloqué par le pare-feu. Quelle solution est la plus conforme ?

  • A. Désactiver le pare-feu
  • B. Ajouter à la liste d'autorisation seulement l'hôte du registre nécessaire, ou préinstaller les dépendances dans copilot-setup-steps
  • C. Autoriser tous les hôtes
  • D. Demander à l'agent de contourner
Correction

B. Moindre privilège réseau, ou installation en amont.

  • A et C ✗ ouvrent l'exfiltration.
  • D ✗ encourage le contournement d'une protection.
Cas 32 · Réessayer une action non idempotente

Une étape « envoyer l'e-mail de facturation » échoue par time-out. Le script réessaie 10 fois sans vérifier. Risque ?

  • A. Aucun
  • B. Doublons : action non idempotente ; vérifier l'état avant, borner les tentatives, puis escalader
  • C. Trop de logs
  • D. Erreur de permissions
Correction

B. Le time-out ne dit pas si l'e-mail est parti : on peut le renvoyer dix fois.

  • A ✗ ignore l'effet répété.
  • C et D ✗ secondaires ou sans rapport.
Cas 33 · Revenir en arrière après un mauvais déploiement

La production est cassée après la fusion de la PR #412. Quelle action est la plus sûre ?

  • A. git reset --hard puis push --force sur main
  • B. git revert par PR, ou redéploiement du dernier SHA sain via l'environnement protégé
  • C. Supprimer la branche main
  • D. Demander à l'agent de réparer en production
Correction

B. On annule sans réécrire l'histoire et on passe par un chemin contrôlé.

  • A ✗ réécrit l'historique.
  • C ✗ destructeur.
  • D ✗ action irréversible laissée à l'agent.
Cas 34 · Les workflows ne se lancent pas sur la PR de l'agent

La PR du cloud agent n'a aucun check lancé. Pourquoi ?

  • A. Bug GitHub
  • B. Les workflows attendent l'action « Approve and run workflows » par un humain
  • C. L'agent n'a pas poussé
  • D. Les checks sont désactivés pour les brouillons
Correction

B. Garde-fou par défaut : l'humain autorise l'exécution du code de l'agent.

  • A ✗ comportement voulu.
  • C ✗ la PR existe, donc il a poussé.
  • D ✗ les brouillons déclenchent bien des workflows.

Domaine 3 · Mémoire, état et exécution

Cas 35 · Deux sources contradictoires

Le README dit « Node 18 », la CI utilise Node 20. L'agent doit écrire un script de build. Meilleure conduite ?

  • A. Suivre le README
  • B. Considérer la CI (source exécutable) comme plus fiable, signaler la contradiction et proposer la correction du README
  • C. Choisir au hasard
  • D. Cesser tout travail
Correction

B. Hiérarchie de sources : ce qui s'exécute prime sur la documentation, et le conflit est remonté.

  • A ✗ la documentation peut être périmée.
  • C ✗ aucune méthode.
  • D ✗ bloque sans nécessité.
Cas 36 · Session interrompue au milieu d'un lot

Une session de 4 heures s'arrête. Que doit faire la reprise ?

  • A. Tout recommencer
  • B. Relire plan et journal, vérifier l'état réel du dépôt, reprendre au dernier point validé
  • C. Se fier à ce dont l'agent « se souvient »
  • D. Reprendre au hasard
Correction

B. L'état durable est externe, et on vérifie le réel avant d'agir.

  • A ✗ perte de travail et risque de doublons.
  • C ✗ la mémoire de session est perdue.
  • D ✗ aucune garantie.
Cas 37 · Dérive en fin de longue session

Après 3 heures, l'agent oublie une contrainte posée au début. Quelle mesure est la plus robuste ?

  • A. Répéter la contrainte oralement de temps en temps
  • B. Écrire les contraintes dans un fichier de plan relu à chaque étape, et découper en lots courts
  • C. Augmenter la créativité du modèle
  • D. Ignorer le problème
Correction

B. Contexte long = dérive ; la contrainte vit dans un artefact.

  • A ✗ dépend de la mémoire de session.
  • C ✗ aggrave la dérive.
  • D ✗ non-réponse.

Domaine 4 · Évaluation et ajustement

Cas 38 · « Tous les tests passent »

L'agent écrit dans la PR « tous les tests passent ». Que vérifier d'abord ?

  • A. Rien, c'est son rôle
  • B. Le résultat réel du check CI
  • C. Le ton du message
  • D. Le nombre de commits
Correction

B. La preuve prime sur l'affirmation.

  • A ✗ un agent peut se tromper ou halluciner.
  • C et D ✗ ne prouvent rien.
Cas 39 · Choisir des indicateurs

Pour évaluer un agent de correction de bugs, quelle combinaison est la plus pertinente ?

  • A. Nombre de lignes générées
  • B. Taux de PR dont les checks passent du premier coup, délai de résolution, coût, retours de revue
  • C. Seulement la satisfaction déclarée
  • D. Nombre de commits
Correction

B. Signaux quantitatifs et qualitatifs, mesurables, liés à l'objectif.

  • A et D ✗ mesurent l'activité, pas la valeur.
  • C ✗ un seul signal subjectif.
Cas 40 · Classer la cause racine

L'agent échoue systématiquement à lancer les tests : « command not found: playwright ». Cause racine ?

  • A. Raisonnement
  • B. Environnement (outil non installé dans les étapes de préparation)
  • C. Contexte périmé
  • D. Permission de dépôt

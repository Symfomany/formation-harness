Scénarios d'examen

Vingt situations concrètes, au format des examens blancs : mémoire, contrôles de politique, relecteurs, workflow multi-agents, workflow de rollback, workflow « les tests passent », PR de déploiement générée par Copilot, rollback par SHA.

Répondre avant d'ouvrir la correctionChaque correction : réponse, pourquoi, piège
Méthode pour chaque cas
  1. Identifier le domaine et le risque réel.
  2. Éliminer les réponses qui reposent sur une consigne, un souvenir de l'agent ou une approbation inutile.
  3. Choisir le mécanisme qui impose, avec le moindre privilège et une trace.

Mémoire

Cas 1 · Un fait mémorisé est devenu faux

Après une refonte, Copilot code review continue de recommander l'ancienne convention de journalisation, mémorisée comme fait du dépôt. Que faire en premier ?

  • A. Ajouter « ignore ta mémoire » dans copilot-instructions.md
  • B. Supprimer le fait erroné dans les réglages Copilot Memory du dépôt, et documenter la nouvelle convention dans les instructions
  • C. Désactiver Copilot code review
  • D. Attendre 28 jours que le fait expire
Correction

B. Les propriétaires du dépôt peuvent supprimer un fait. Écrire la convention dans les instructions évite qu'elle soit réapprise à tort.

Piège : D est vrai en théorie (28 jours sans usage), mais le fait est justement utilisé, donc son délai repart. Et attendre n'est pas une correction.

Cas 2 · Une migration sur plusieurs jours et plusieurs outils

Une migration dure trois jours. Elle passe de VS Code à la CLI, puis au cloud agent. Les décisions doivent être reprises sans être rediscutées, et auditées. Quelle mémoire ?

  • A. Copilot Memory
  • B. Une longue session de chat jamais fermée
  • C. Un plan et un journal versionnés dans le dépôt (ou la description de la PR)
  • D. Les préférences personnelles de l'utilisateur
Correction

C. Mémoire externe, durable, partagée par tous les outils, auditable.

Piège : A semble séduisant, mais Copilot Memory est inférée par Copilot, expire et n'est pas un registre de décisions. B est résumée automatiquement et non partageable.

Cas 3 · La préférence personnelle ignorée en revue

Une développeuse a une préférence mémorisée (« tests en style Given/When/Then »). Copilot code review ne l'applique pas sur ses PR. Pourquoi ?

Correction

Copilot code review n'utilise que les faits du dépôt, pas les préférences personnelles. Pour une règle d'équipe : fichier d'instructions (applyTo sur les tests), en gardant à l'esprit que code review ne lit que les 4 000 premiers caractères.

Contrôles de politique

Cas 4 · Le check requis reste « en attente »

Le check « Tests » est requis par un ruleset. Une PR qui ne modifie que la documentation est bloquée : le check reste Expected — Waiting for status to be reported. Cause ?

  • A. Le runner est saturé
  • B. Le workflow a un filtre paths : il ne démarre pas, le statut n'arrive jamais
  • C. Copilot n'a pas approuvé la PR
  • D. Il manque contents: write
Correction

B. Retirer le filtre paths du workflow requis, ou filtrer à l'intérieur du job (un job qui se termine en succès reste un statut).

Piège : un job sauté par une condition rapporte un succès ; un workflow jamais déclenché ne rapporte rien.

Cas 5 · Empêcher un agent de modifier les workflows

Vous voulez qu'aucune modification de .github/workflows/ ne soit fusionnée sans l'équipe plateforme, qu'elle vienne d'un agent ou d'un humain. Quelles mesures imposent cette règle ? (deux réponses)

  • A. Une phrase dans copilot-instructions.md
  • B. CODEOWNERS sur .github/workflows/ + ruleset « Require review from Code Owners »
  • C. Un ruleset qui exige une PR et bloque le push direct et le push forcé sur la branche par défaut
  • D. Demander à Copilot code review de surveiller ces fichiers
Correction

B et C. Un hook preToolUse peut s'ajouter en défense en profondeur côté agent.

Piège : A et D guident ou commentent, ils n'empêchent rien.

Cas 6 · N'autoriser que des serveurs MCP approuvés

L'entreprise veut que les développeurs n'utilisent que des serveurs MCP validés par la sécurité. Que configurer ?

Correction

Un registre MCP contenant les serveurs approuvés, et la politique Registry only au niveau organisation ou entreprise (au lieu de Allow all). Côté cloud agent : liste tools explicite et secrets COPILOT_MCP_.

Piège : désactiver complètement MCP « par sécurité » bloque aussi les usages légitimes : réponse trop large.

Relecteurs

Cas 7 · « Je ne peux pas approuver ma PR »

Paul a assigné une issue à Copilot. La PR est prête, Paul est le seul relecteur de l'équipe ce jour-là, le bouton d'approbation est inopérant. Pourquoi, et que faire ?

Correction

Celui qui a demandé la tâche au cloud agent ne peut pas approuver la PR : cela préserve la règle « approbations requises ». Il faut un autre relecteur. Si la PR n'est attribuée à personne (ouverte sous l'identité de l'application), une approbation supplémentaire est exigée.

Piège : contourner via un bypass ou en désactivant la règle.

Cas 8 · La revue de Copilot compte-t-elle ?

Le ruleset exige 1 approbation. Copilot code review a relu la PR sans rien trouver. La PR peut-elle être fusionnée ?

Correction

Non. Copilot code review laisse une revue de type Comment, jamais Approve ni Request changes. Elle ne compte pas dans les approbations requises.

Workflow multi-agents

Cas 9 · Deux agents, un même fichier

Deux issues sont assignées en parallèle au cloud agent. Les deux PR modifient config/routes.ts et entrent en conflit. Quelle est la meilleure prévention pour la suite ?

  • A. Lancer plus d'agents pour finir plus vite
  • B. Découper les tâches par périmètres de fichiers disjoints, ou séquencer celles qui touchent la même zone
  • C. Laisser le second agent forcer sa version
  • D. Fusionner les deux PR sans revue pour éviter le conflit
Correction

B. Résolution immédiate : fusionner la première, puis mettre à jour la seconde sur la base à jour (par exemple en demandant à @copilot de résoudre le conflit) et la relire.

Cas 10 · Deux agents se contredisent

Le reviewer déclare US-204 conforme ; le contrôleur la déclare non conforme. L'orchestrateur propose de garder l'avis majoritaire de trois agents.

Correction

Mauvaise idée. Bonne réponse : critère déterministe commun (ici verifier-us.cjs), puis arbitrage humain si le désaccord porte sur le fond. Documenter la décision dans le journal.

Cas 11 · L'orchestrateur tourne en rond

Un schéma producteur-critique tourne depuis 40 minutes : le critique refuse, le producteur reformule, sans fin.

Correction

Exécution bloquée. Borner le nombre de tours (2 ou 3), puis escalader à un humain avec les deux versions et la raison du refus. Côté hooks : le blocage de fin (agentStop) est limité à 8 fois, et stop_hook_active doit être respecté.

Workflow « les tests passent »

Cas 12 · « Tous les tests passent », dit l'agent

La PR du cloud agent indique « tous les tests passent ». Aucun check n'apparaît dans l'onglet des checks.

  • A. Fusionner : l'agent a lancé les tests
  • B. Relire le code, puis cliquer Approve and run workflows ; fusionner seulement si les checks requis sont verts
  • C. Demander à l'agent de relancer les tests
  • D. Désactiver les checks requis pour cette PR
Correction

B. Par défaut, les workflows ne tournent pas sur le code du cloud agent tant qu'un utilisateur avec accès en écriture ne les a pas approuvés. La preuve, c'est le check, pas la phrase de l'agent.

Cas 13 · L'agent ne peut pas lancer les tests

Le journal de session montre que l'agent n'arrive pas à installer les dépendances : délai réseau sur un registre interne.

Correction

Cause d'environnement. Préinstaller les dépendances dans copilot-setup-steps.yml (job copilot-setup-steps, branche par défaut), et/ou ajouter le registre à la liste autorisée du pare-feu. Ne pas réécrire le prompt : ce n'est pas un problème de raisonnement.

PR de déploiement générée par Copilot

Cas 14 · Copilot modifie le workflow de déploiement

Le cloud agent ouvre une PR qui modifie deploy.yml pour ajouter une étape. Quelles protections doivent jouer avant qu'un déploiement en production ait lieu ? (trois réponses)

  • A. Revue obligatoire des propriétaires de .github/workflows/ (CODEOWNERS)
  • B. Relire le diff avant « Approve and run workflows », car le workflow modifié s'exécuterait avec les droits du dépôt
  • C. Environnement production avec approbateurs, auto-approbation interdite, branche main seulement
  • D. Laisser Copilot fusionner après les checks verts
Correction

A, B et C. D est impossible : le cloud agent ne fusionne jamais.

Piège : cliquer « Approve and run workflows » sans relire, c'est exécuter du code de workflow non relu.

Cas 15 · Le déploiement casse la production

La PR de Copilot a été fusionnée et déployée. La production est en erreur. Que faire en premier ?

  • A. git reset --hard sur main puis push --force
  • B. Relancer le déploiement avec le SHA du dernier déploiement sain (approbation de l'environnement), puis ouvrir une PR de git revert
  • C. Demander à Copilot de corriger directement en production
  • D. Supprimer l'environnement
Correction

B. D'abord restaurer le service avec un état connu (SHA visible dans l'historique de déploiement), ensuite corriger l'historique proprement par revert et PR.

Workflow de rollback et rollback par SHA

Cas 16 · La PR de rollback n'a pas de checks

Le workflow de rollback crée une PR avec GITHUB_TOKEN. Les checks requis restent en attente, aucun workflow pull_request ne démarre.

Correction

Les événements créés avec GITHUB_TOKEN ne déclenchent pas de nouveaux workflows (sauf workflow_dispatch et repository_dispatch). Solutions : jeton d'une GitHub App dédiée, ou action humaine (commit, fermer/rouvrir). Pré-requis pour créer la PR : réglage « Allow GitHub Actions to create and approve pull requests ».

Cas 17 · Annuler un commit de fusion

Le SHA à annuler est un commit de fusion. Quelle commande ?

  • A. git reset --hard <sha>~1
  • B. git revert <sha>
  • C. git revert -m 1 <sha>
  • D. git cherry-pick <sha>
Correction

C. -m 1 indique de garder le premier parent (la branche cible). B échoue sur un commit de fusion. A réécrit l'historique.

Cas 18 · Le SHA saisi dans le formulaire

Un workflow de rollback contient : run: git revert ${{ inputs.sha }}. Quel est le risque, et la correction ?

Correction

Injection de commande : l'expression est remplacée avant l'exécution du shell. Correction : passer par env: SHA: ${{ inputs.sha }}, utiliser "$SHA", valider le format (40 caractères hexadécimaux) et vérifier que le commit appartient à la branche par défaut.

Garde-fous

Cas 19 · Le hook de sécurité laisse passer

Un hook preToolUse scanne tout le dépôt avant chaque écriture. Sur un gros dépôt, il met 45 s. Les écritures interdites passent. Pourquoi ?

Correction

Délai par défaut de 30 s dépassé : un timeout est toujours fail-open. Rendre le hook rapide (ne regarder que l'outil et le chemin), ajuster timeoutSec raisonnablement. Un plantage ou un code de sortie non nul, lui, refuse.

Cas 20 · Trop d'approbations

L'équipe exige une approbation manuelle pour chaque commande terminal de l'agent, y compris ls et git status. Les livraisons ralentissent. Meilleure réponse ?

  • A. Tout approuver automatiquement
  • B. Approuver automatiquement les commandes en lecture, refuser les commandes dangereuses par hook, garder l'humain sur fusion et déploiement
  • C. Interdire le terminal à l'agent
  • D. Garder la règle actuelle
Correction

B. Le guide demande de « minimiser les approbations qui ne réduisent pas le risque de façon significative ».
